project : Project Description: This project implements a DNS resolver that sends and receives DNS packets using an AF_XDP (XSK) socket instead of the usual UDP/TCP socket. An XDP program attached to the NIC redirects DNS traffic (UDP dst port 53) to an AF_XDP socket; a user-space resolver crafts raw Ethernet/IPv4/UDP/DNS frames, transmits them via the XSK TX ring, and receives responses on the XSK RX ring. The project demonstrates low-latency, high-throughput packet I/O, zero-copy packet handling tradeoffs, and the extra plumbing required (UMEM, rings, descriptor management) compared to conventional sockets. Tools / Technologies Linux kernel AF_XDP / XDP support (recent kernel) clang/llvm (for compiling the XDP BPF program) libbpf / libxsk (or equivalent XSK helper code) for user-space XSK setup C (user-space resolver) for packet crafting and XSK ring handling bpftool / xdp-loader (to load/attach the XDP program) tcpdump / Wireshark / pkt-gen (for validation and packet inspection) Expected Outcome: Comparison vs standard UDP sockets: measurements of latency, throughput, and CPU overhead showing AF_XDP tradeoffs (zero-copy performance benefits vs implementation complexity).

Two things I had to decide before writing anything, both of which change the answer:

The brief says "BPF array", but the cache isn't in BPF. af_xdp_kern.c only classifies and redirects — it does no cache lookup, and there's no BPF map cache to guard. A filter there could only tell the kernel "this name isn't cached," and since a miss has to reach userspace to be resolved anyway, it would save nothing while adding a userspace→kernel sync problem. The map worth guarding is dns_cache.c's userspace hash table, so that's where I put it. (If you want the kernel-side version anyway for the report, BPF_MAP_TYPE_BLOOM_FILTER exists natively since 5.16 — say the word.)

A plain Bloom filter is wrong for this cache. Your cache deletes: LRU eviction and TTL expiry both remove entries. A plain bit filter can't clear a bit without risking a false negative for some other key sharing it, so bits only accumulate, FPR climbs to 1, and the filter decays into a branch that always says "maybe" — it would pass a naive test suite and quietly stop working in production. I used a counting filter: 65536 one-byte counters (64 KiB), k=4, m/n=16 at your 4096-entry capacity → analytic FPR ≈ 0.24%. One byte per slot rather than packed nibbles so updates are atomic without a read-modify-write straddling two counters.

The saving isn't the hash — it's the mutex. A cold query now answers with four relaxed byte loads and never takes the lock. Reads are lock-free; updates ride the existing cache mutex. Both race directions are benign (detailed in the comments), and it's clean under TSan.

Measured, 4 threads, 2M lookups (single-CPU container, so contention is serialised and this understates the multi-core case):

cold %	bloom Mlookup/s	no-bloom	ratio
99	22.9	14.7	1.55×
90	17.2	11.8	1.45×
50	7.69	7.56	1.02×
0	4.96	5.49	0.90×
The last row is the honest finding and belongs in your report: on an all-hit workload the filter is pure overhead, ~10% slower. It pays only when miss rate is high. Measured FPR came out at 0.255% against the 0.24% analytic bound.

Testing — three layers, all in make test (212 checks, 0 failures under ASan+UBSan):

test_bloom() — no-false-negatives, counting semantics (add twice / delete once must still read present, the exact case a plain filter fails), full add-then-delete churn leaving zero slots set, and measured-vs-analytic FPR over 100k probes.
test_bloom_cache_sync() — the one that matters: drives 3× capacity through the LRU and asserts reachable entries == live entries through the public cache API. A filter that's incremented but never decremented passes every isolated test and fails here.
make bench — A/B sweep. bench_bloom and bench_nobloom from one source via -DDNS_BLOOM_DISABLED, compile-time not runtime so neither binary carries the other's branch. Names are pre-generated outside the timed loop; snprintf inside it was costing ~300 ns/op and burying the effect.
dns_backend_fini() now also prints bloom lookups, reject rate, slots used, and a saturation warning if the filter is ever undersized.

One thing I noticed but didn't touch: dns_cache_init() zeroes the bucket table without freeing existing nodes, so calling it twice leaks. Pre-existing, and my test works around it with an explicit fini().

You were right to push. There was real overhead and it was my fault.

The bug. I instrumented the filter with three shared _Atomic counters and fetch_add'ed them on every lookup. That's a lock-prefixed read-modify-write on a cache line every worker writes — the exact shared-write cost the filter exists to avoid, reintroduced by its own bookkeeping. Isolated microbenchmark:

scattered + atomic counters    14.58 ns
scattered, no counters          4.90 ns
~10 ns per lookup uncontended, much worse with four threads. Fixed by sharding stats one cache line per thread. Each thread is the sole writer to its shard, so the relaxed load/store pair compiles to plain mov with no lock prefix; readers sum the shards.

I also tried a blocked layout (all k slots inside one cache line, 1 miss instead of 4). It measured worse — 41.6 vs 34.2 ns on the cold path — because the dedupe needed for add/del symmetry costs more than the misses it saves, 64 KiB largely sitting in L2. Discarded it rather than keep a plausible-sounding optimisation that doesn't pay.
